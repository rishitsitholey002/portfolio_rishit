End-to-End Data Pipeline — Snowflake & Dimensional Modeling

A complete ELT platform: multi-source raw data ingested into Snowflake, modeled into a documented star schema, and validated on every load — built to prove one thing: that a single engineer can own the entire path from landing zone to analytics-ready warehouse.

Executive summary

Analytical questions — revenue by segment, trend by period, performance by dimension — kept requiring fresh ad-hoc queries against raw, inconsistent source extracts. Each answer was slow to produce and impossible to reproduce. The fix wasn't another query; it was a warehouse: one modeled, validated, documented layer that any reporting tool could sit on top of.

How it started

Raw data arrived from multiple sources in different shapes — inconsistent types, duplicate business keys, missing values. Rather than cleaning it per-report, I designed an ELT flow that lands everything raw, transforms it once inside Snowflake, and exposes a star schema as the single interface for analytics.

Business requirements

  • All source data centralized in one queryable warehouse instead of scattered files.
  • Reporting queries must be repeatable — same question, same answer, any day.
  • Duplicates and bad records caught before they reach analytical tables.
  • The model documented well enough that a new analyst can self-serve.
  • Loads re-runnable and incremental — no full reloads for daily updates.

Outcome

100K+ records flowing through a four-layer warehouse (raw → staging → warehouse → marts), modeled into one fact table with multiple conformed dimensions, with validation gates on every load and a documented warehouse layer for repeatable reporting.

System architecture

Sources land in cloud storage, Python orchestrates extraction and file hygiene, and Snowflake does the heavy lifting — staging via COPY INTO, transformation in SQL, and a star schema published to the BI layer.

Blue packets: data in motion. Amber: business value leaving the warehouse.

Extract → Load → Transform, with guardrails

Extract. Python collects files from S3 and database extracts, verifies row counts against source, and writes structured logs for every batch. Failures raise, retry with backoff, and never fail silently.

Load. Files land in a Snowflake external stage and load via COPY INTO staging tables — typed columns, load timestamps, and batch IDs on every row so any record can be traced to its source file.

Transform. SQL inside Snowflake handles deduplication (window functions over business keys), conforming types and categories, and building the star schema with MERGE for incremental upserts — only changed records move, never full reloads.

Validate. Post-load checks assert primary-key uniqueness, referential integrity between fact and dimensions, row-count reconciliation, and freshness. A failed check stops the run before dashboards see it.

Schedule & monitor. Jobs run scheduled and on-demand; each run logs start, end, rows in/out, and validation results — the same run-history pattern this page's experience section is styled after.

Design rule: the pipeline is idempotent. Re-running any batch produces the same warehouse state — which is what makes 2 a.m. incident recovery boring instead of terrifying.

Star schema at a declared grain

The fact table's grain is one row per transactional line item. Dimensions carry the descriptive context; the fact carries keys and measures only. Surrogate keys insulate the model from source-system key changes, and business keys are preserved for traceability.

SCD handling. Customer attributes that change over time (like segment) are tracked as Type 2 — new row per change with valid_from / valid_to / is_current — so historical facts join to the customer as they were, not as they are.

Deduplication with window functions

Source extracts can deliver the same order multiple times with different update timestamps. This keeps exactly the latest version of each business key — the single most common transform in the pipeline.

transform/dedupe_orders.sqlSNOWFLAKE SQL
WITH ranked AS (
  SELECT
    s.*,
    ROW_NUMBER() OVER (
      PARTITION BY order_id, line_number   -- business key
      ORDER BY updated_at DESC, _loaded_at DESC
    ) AS rn
  FROM stg_orders s
)
SELECT * FROM ranked WHERE rn = 1;

Incremental upsert into the fact

Only new or changed rows touch the fact table. MERGE keys on the business key; measures update in place, new lines insert.

load/merge_fct_sales.sqlSNOWFLAKE SQL
MERGE INTO fct_sales f
USING transformed_orders t
  ON f.order_id = t.order_id AND f.line_number = t.line_number
WHEN MATCHED AND t.updated_at > f.updated_at THEN UPDATE SET
  quantity = t.quantity, unit_price = t.unit_price,
  revenue = t.revenue, updated_at = t.updated_at
WHEN NOT MATCHED THEN INSERT
  (sales_key, date_key, product_key, customer_key,
   channel_key, order_id, line_number, quantity,
   unit_price, revenue, updated_at)
VALUES (...);

Validation: orphan-key check

Referential integrity isn't enforced by constraints in analytical warehouses — so it's asserted after every load. Any fact row whose key can't find its dimension fails the run.

validate/orphan_keys.sqlSNOWFLAKE SQL
SELECT COUNT(*) AS orphan_rows
FROM fct_sales f
LEFT JOIN dim_product p ON f.product_key = p.product_key
WHERE p.product_key IS NULL;
-- expected: 0. Anything else halts the pipeline.

Extraction with logging, retries, and no silent failures

The Python layer's job is boring reliability: fetch, verify, log, hand off. Reusable functions, structured logging, and explicit exception handling — every batch leaves a paper trail.

pipeline/extract.pyPYTHON
import logging, time
import pandas as pd

log = logging.getLogger("pipeline.extract")

def with_retry(fn, attempts=3, backoff=2.0):
    """Retry transient failures with exponential backoff."""
    for i in range(attempts):
        try:
            return fn()
        except Exception as exc:
            if i == attempts - 1:
                log.error("failed after %s attempts: %s", attempts, exc)
                raise
            log.warning("attempt %s failed, retrying", i + 1)
            time.sleep(backoff ** i)

def clean_orders(df: pd.DataFrame) -> pd.DataFrame:
    """Type-cast, trim, and normalise raw order extracts."""
    df = df.rename(columns=str.lower)
    df["order_date"] = pd.to_datetime(df["order_date"], errors="coerce")
    df["revenue"] = pd.to_numeric(df["revenue"], errors="coerce")
    before = len(df)
    df = df.dropna(subset=["order_id", "order_date"])
    log.info("cleaned %s rows, dropped %s", len(df), before - len(df))
    return df

def validate_batch(df: pd.DataFrame, expected_rows: int) -> None:
    """Fail loudly if the batch doesn't reconcile with source."""
    if len(df) < expected_rows * 0.99:
        raise ValueError(
            f"row count {len(df)} below expected {expected_rows}")

Each function does one job and is testable in isolation — the same functions serve scheduled runs and on-demand backfills.

How the warehouse is put to work

Storage vs. compute. Snowflake separates them: data lives once in columnar storage; virtual warehouses spin up to query it. Loads run on a dedicated warehouse so a heavy transform never slows a analyst's query — and both suspend when idle, so cost tracks usage.

Stages & COPY INTO. Files land in an external stage pointed at cloud storage; COPY INTO loads them with file-format handling and load-history tracking, which makes reloads safe — Snowflake skips files it has already ingested.

load/stage_and_copy.sqlSNOWFLAKE SQL
CREATE STAGE IF NOT EXISTS landing
  url = 's3://landing/sales/'
  file_format = (TYPE = CSV skip_header = 1);

COPY INTO stg_orders
FROM @landing
PATTERN = '.*2026-07.*[.]csv'
ON_ERROR = 'ABORT_STATEMENT';  -- bad file = stopped load, not bad data

Query performance. The star schema itself is the first optimization — narrow fact, small dimensions, integer key joins. Beyond that: pruning-friendly filters on date keys, avoiding SELECT * in transforms, and reading the query profile to find the expensive step instead of guessing.

Continuous ingestion via Snowpipe is the natural next step for this design — the stage/COPY structure is already Snowpipe-shaped; it's a matter of attaching the pipe when latency requirements justify it.

What changed

Repeatable

The same business question returns the same answer every time — queries hit a documented model, not ad-hoc extracts.

Self-serve

A documented warehouse layer means analysts answer questions from the schema instead of asking the pipeline owner.

Trustworthy

Validation gates on every load mean bad data stops in staging — dashboards only ever refresh from clean tables.

Lessons learned

Technical

Idempotency is a design decision, not a feature you add later. MERGE-based loads made reruns safe from day one.

Architecture

Declaring the fact grain first prevented every downstream modeling argument. Grain is the contract.

Business

A warehouse nobody can navigate is a data swamp with better marketing — documentation is part of the deliverable.

Performance

The cheapest query is the one the model makes unnecessary. Good dimensional design beats clever SQL tuning.

Executive summary

Four business domains — finance, sales, marketing, supply chain — each looked at the same underlying transactions through different spreadsheets and reached different numbers. The suite's job was to make disagreement impossible: one modeled dataset, one set of DAX measures, and connected dashboards where every domain drills into the same 2.2M+ records.

Business requirements

  • Executives wanted a single top-level view with drill-through into each domain.
  • KPIs had to be defined once — the same "revenue" everywhere, no per-report formulas.
  • 2.2M+ MySQL records needed shaping into a model Power BI could query fast.
  • Each domain team needed its own workspace without forking the metric definitions.

Approach

Transactions were transformed from MySQL into a dimensional model, imported into Power BI, and every KPI written as a central DAX measure. Dashboards share the model: the finance page, the sales page, and the executive summary all compute from identical measures — bookmarks and drill-through connect them into one navigable product rather than ten disconnected reports.

Measures defined once, used everywhere

The core discipline of the suite: no visual carries its own formula. Every number on every page resolves to a named measure in the model.

model/measures.daxDAX
-- Base measure: single definition of revenue
Total Revenue = SUM ( fct_sales[revenue] )

-- Time intelligence built on the base, not beside it
Revenue LY =
  CALCULATE ( [Total Revenue], SAMEPERIODLASTYEAR ( dim_date[date] ) )

Revenue YoY % =
  DIVIDE ( [Total Revenue] - [Revenue LY], [Revenue LY] )

-- Running total for the cumulative trend visuals
Revenue YTD =
  TOTALYTD ( [Total Revenue], dim_date[date] )

-- Contribution: share of the current filter context
Revenue % of Total =
  DIVIDE (
    [Total Revenue],
    CALCULATE ( [Total Revenue], ALL ( dim_product ) )
  )

When finance asks "why does my number differ from sales?", the answer is: it can't. Both pages call [Total Revenue].
